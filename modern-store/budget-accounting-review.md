# Учёт выходных файлов image worker

При первоначальной локальной доработке учёта изменён только `image-build-source.php`; на этом этапе сайт и браузер не менялись. Существующая очередь, курсор, manifest/map-файлы и готовые WebP сохраняются. Результат последующей серверной проверки миграции указан ниже.

## Что изменено

- `output_accounting_version = 1` и `output_dirty` хранятся в том же атомарном `state.php`, что точный `output_bytes` и курсор.
- Обычный пакет доверяет только неотрицательному целочисленному счётчику известной версии с `output_dirty === false`. Полный обход каталога остаётся для миграции старого state, dirty recovery и явного `prepare`.
- Перед обработкой пакета и перед записью публичного конфигурационного файла атомарно сохраняется `output_dirty = true`. Если запись state не удалась, публичные файлы не создаются.
- Только нормальное завершение пакета/prepare одним атомарным commit сохраняет счётчик, курсор и `output_dirty = false`. Обработчики ошибок, shutdown и pause не снимают dirty.
- Полный пересчёт учитывает все обычные файлы, в том числе `.htaccess`, остаточные временные файлы и WebP, не попавшие в manifest. Symlink/каталог внутри output по-прежнему вызывает остановку при пересчёте.
- Неудачное удаление публичного временного файла теперь останавливает пакет с dirty, чтобы последующие записи не использовали заниженный счётчик.
- Новый незавершённый `prepare` имеет `prepare_complete = false` и не допускает `run` до успешного окончания подготовки. Отсутствующее поле у уже работающей старой очереди сохраняет совместимость.

## Сохранённые ограничения

600 MiB (`629145600` байт), проверка свободного места при каждом budget и перед новым WebP, резерв 16 MiB перед вариантом, 2400 секунд суммарного CPU (финальная настройка; при первоначальной проверке фикса было1800), пакет до 2 CPU / 4 wall секунд / 20 групп, пауза интерфейса 1000 ms, общий mutex, авторизация/CSRF, ограничения входных изображений и сохранность оригиналов не изменены. Новый `.htaccess` также проверяется на вместимость до создания временного файла.

## Разбор прерываний

| Момент сбоя | Состояние на диске и восстановление |
| --- | --- |
| До успешной записи dirty | Новых публичных файлов ещё нет; прежний clean-счётчик точен. |
| После dirty, до создания temp | Следующий обрабатывающий пакет выполнит лишний, но безопасный полный пересчёт. |
| Во время записи temp | Dirty остаётся; пересчёт включит фактический размер частичного файла. |
| После rename WebP, до прибавления размера | Dirty остаётся; готовый orphan учитывается пересчётом, поэтому потеря прибавления не занижает следующий бюджет. |
| После прибавления размера/изменения курсора, до финального commit | Старый state остаётся dirty; полный пересчёт восстанавливает байты. Старый курсор может повторить группу; существующие WebP проверяются и не записываются заново. |
| Ошибка записи clean commit | Предыдущий дисковый state уже dirty; флаг в памяти также возвращается в true до обработки ошибки. |
| Fatal/shutdown | Dirty принудительно сохраняется; best-effort сохранение прочего состояния остаётся прежним. |
| Ошибка удаления публичного temp | Пакет прекращает новые записи и оставляет dirty; остаток будет учтён при восстановлении. |
| Ошибка нового prepare | Сохранённый `prepare_complete = false` запрещает запуск; повторный prepare заново пересчитает каталог. |
| После успешного clean commit | Все постоянные новые файлы прибавлены, временные удалены; байты и курсор сохранены вместе. |

Остановочные статусы (`failed`, `cpu_limit`, `output_budget`, `done`) сохраняют прежнее поведение. Запрос, который только показывает остановочный статус, не изменяет output и не снимает dirty. Полный пересчёт произойдёт при следующем разрешённом обрабатывающем запуске либо явном prepare.

## Выполненная проверка

- Статические assertions подтвердили неизменность лимитов CPU/пакета/байтов/паузы, двух явных clean commit и порядок dirty перед публичными записями.
- Отдельная модель прерываний перебрала 8 границ записи: clean-счётчик всегда равен фактическим файлам, а dirty recovery включает temp/orphan. Старый, dirty и некорректный счётчик не попадает в доверенную ветку. Это модель протокола, не выполнение PHP worker.
- Независимый read-only review не выявил окна занижения счётчика; замечание о вместимости нового `.htaccess` учтено.
- PHP CLI/парсер в локальной среде отсутствует: PHP lint и GD/runtime-тест не заявляются.

После остановки предыдущей версии миграция проверена на сервере: первый успешно завершённый пакет показал `accounting_version: 1`, `accounting_dirty: false`, `accounting_full_scan: true`; следующий — `accounting_full_scan: false` с продолжающимся курсором. Если первый пересчёт съест весь wall-бюджет, он всё равно завершит миграционный clean commit, поэтому следующий пакет начнёт без полного обхода.

Гарантия счётчика предполагает эксклюзивное владение этим output-каталогом worker под его mutex. Ручные добавления файлов другим процессом требуют явного prepare/пересчёта. Протокол покрывает прерывание PHP-процесса; абсолютная устойчивость к сбою питания без fsync файлов и каталога не обещается.
