## Cache proposal

Files: `FacetOptionsCache.php`, `hostcms-facet-cache-adapter.php`, `catalog-facets.patch`, `tests/facet-cache-test.php`.

The native cache module page names Business/Corporation, while the SmallBusiness marketing page contains a generic caching block. This conflict does not prove availability in the installed licence. Official cache examples require `Core::moduleIsActive('cache')`; do not force activation or instantiate a paid driver directly. Native `Core_Cache_Memory` stores a PHP object array for the request, not a persistent TTL cache. This proposal is independent project code and uses no HostCMS cache driver/configuration.

The adapter reuses the existing native **shop-scoped `$defs` array**, avoiding a second ORM relation/query mutation. It requires CURRENT_SITE2 / Shop1, exact IDs/names and string type1. Missing/mismatched/list definitions return NULL and preserve the existing native branch. Brands stay fresh through the existing producer query, including current active-brand validation.

One fixed cache file stores only `{22:[strings],28:[strings],39:[strings]}`. TTL is fixed at300s maximum, without sliding refresh. The key contains Site2/Shop1, a recipe generation and canonical definition metadata; it never includes request/cart/user/filter parameters. Definition changes miss immediately; value edits become visible within the TTL, or immediately after explicit `invalidate()`/generation change. Bump the recipe generation after changing option-building rules. No native hooks or public clear endpoint are installed. TTL/manual invalidation is bounded eventual consistency, not immediate invalidation of every database edit; use60s during frequent edits if needed.

The provisioned exclusive directory must already exist, be canonical and not group/world writable. The component never mkdir/chmod from front-end requests. On this hosting, the image project already needed a guarded CMS-owned storage area because writing outside DOCROOT failed; do not assume that parent directories are writable. Provision helpers/data in their own reserved folder before enabling the source patch, verify direct HTTP denial, then enable the source patch last. Rollback the source patch before removing helpers.

The data file is at most128KiB. A nonblocking mutex serializes writers; lock contention or storage/JSON failure returns freshly built values. JSON is never include/eval'd. A PHP404/exit/__halt_compiler guard is flushed before JSON; same-directory rename publishes a complete file. A single fixed reserved temp under the mutex bounds crash leftovers. Maximum reserved files are cache+temp+lock; old temps are reused/removed under lock. No cache write error masks or repeats a native builder exception. Empty option arrays are valid cache hits; oversize payloads simply are not cached. This is a disposable process-crash-safe cache, not an fsync/power-loss durability guarantee.

Measure before enabling: a hit removes three DISTINCT/group queries, but no PageSpeed or whole-store CPU improvement is claimed. Labels can include values belonging to currently hidden products, matching the current DISTINCT behavior; actual product results retain native visibility restrictions.

## Verified PHP/core facts and remaining blockers

- Official HostCMS changelog lists **7.1.7 stable (12.05.2026)** and **7.1.8 beta (22.10.2026)**. PHP8.5 support was added in7.1.6, so7.1.7 supports8.5 at core level; PHP8.4 was added in7.1.4. This does not prove compatibility of the installed ASMP/custom handlers. Beta is not needed merely to try PHP8.5.
- Beta7.1.8 separately raises minimum PHP to8.1, updates Smarty4.5.8, requires search reindexing and publishes security fixes. Do not mix a beta/core migration with the first PHP runtime switch.
- PHP7.4 is upstream EOL since28.11.2022. PHP8.4 security support runs to31.12.2028; PHP8.5 to31.12.2029. Both are candidates only after isolated application tests.
- Timeweb switches PHP for the **whole website**, immediately. `/modern-*` routes on the existing website cannot isolate a PHP8 trial. CLI/cron interpreter selection is separate. Returning the PHP selector does not undo CMS database migrations.
- Installed ASMP version, native lib80/checkout/payment/delivery/import handlers, other extensions and their vendor changes are not covered by the 19 storefront files. LibraryID103 is not an ASMP version. Confirm the actual installed package before proposing an update.
- Verify the target build's GD/WebP, EXIF, XSL/SimpleXML, mbstring, cURL, mysqli, Zip, Intl and used integrations. PHP8 changes GD/cURL resources to objects; PHP8.4 moves IMAP to PECL. These are checks, not observed production failures.
- The exact fresh baseline image worker calls `imagedestroy()` four times. PHP8.5 deprecates it; PHP8.0+ treats it as a no-op. Before running that worker on8.5, preserve PHP7.4 cleanup conditionally and release object references on8.x. Displayed warnings could pollute JSON; the actual CMS error-handler behavior needs runtime testing. No existing file was patched.
- HostCMS's published database matrix names MySQL5.1–8.0. The observed MySQL8.4.11 is not explicitly covered; seek vendor confirmation, not an assumed incompatibility or database downgrade.
- Support expiry does not end a perpetual SmallBusiness licence. Official updates/support access still depends on the support entitlement; no renewal/purchase or licence change is authorized here.

Before a real PHP switch: approved independent environment/database and recoverable backup; inventory installed integrations; test admin/login, catalog/filter/SEO, two cart sessions, valid coupons, delivery and native checkout in test mode, notifications/payment handlers and imports; record errors/TTFB/CPU; verify rollback. No real order/payment/message is required on production for this proposal.
